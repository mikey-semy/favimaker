**Вывод для развития:** прежде чем добавлять, стоит показать имеющееся. Правка
README сделана — это первый шаг и он бесплатный.

## Что действительно стоит добавить

### Главное: настоящий пользователь здесь — не человек, а агент

Сначала поправка к самому себе: я написал, что людям «достаточно включить
VPN», — это неверно. **Туннель не замена доступности.** Человеку нужно открыть
страницу и получить иконки, а не настраивать обход; на рабочей машине туннель
часто и не поставить. Так что преимущество по доступности настоящее.

Решение не рассказывать о проекте стоит на другом основании, и оно тоже
законное: **автор не видит в нём того, о чём хочется рассказывать.** Это не то
же самое, что «отличия нет».

**А вот у языковых моделей альтернативы нет.** Модель умеет нарисовать SVG — и
на этом останавливается. Она не может:

- отрисовать его в шесть растровых размеров пиксель в пиксель;
- упаковать `favicon.ico` из трёх изображений в один файл;
- посчитать безопасную зону maskable-иконки, чтобы Android не обрезал край;
- собрать набор экранов запуска iOS с media-запросом под каждое разрешение;
- написать `site.webmanifest` и `browserconfig.xml` без ошибок;
- выдать готовый блок для `<head>`, где ничего не забыто.

Это не творческая работа, а детерминированная — ровно то, что favimaker уже
делает и где модель бесполезна. **Разделение простое: модель рисует, инструмент
раскладывает правильно.**

Отсюда и вывод, который меняет приоритет: MCP — не «ещё одна возможность», а
**то, ради чего проект стоит развивать**. У него появляется пользователь,
которого нельзя заменить VPN-ом.

### Как это устроить

**Вход — SVG или эмодзи от модели.** Модель отдаёт строку SVG (или символ
эмодзи), инструмент отдаёт полный набор файлов и кусок для `<head>`.

**Осуществимость проверена по коду.** `lib/renderer.ts` — чистая функция:
конфигурация → canvas, на весь файл одно обращение к `document`. Переносится в
Node почти как есть, если подставить `@napi-rs/canvas`.

| Что | Куда |
|---|---|
| `renderer`, `ico`, `manifest`, `export`, `types`, `og-renderer`, `splash-renderer` | общее ядро, без React и DOM |
| адаптер canvas | два: браузерный и `@napi-rs/canvas` |
| инструменты MCP | `make_icons` (SVG/эмодзи/текст → набор), `make_og_image`, `audit_head` |

Инструменты **пишут файлы прямо в каталог проекта** и возвращают текстом готовый
блок для `<head>` — двоичные данные через протокол гонять не нужно.

**Проверка, которая покажет, что вышло:** попросить Claude завести новый проект
из `project-template` и сделать ему иконки. Если получилось без ручных правок —
инструмент состоялся.

## Чего делать не стоит

**Не превращать в «комбайн для всего веба».** Связь между частями должна быть
понятной: всё, что попадает в `<head>` нового сайта, — да; редактор изображений
общего назначения — нет.

**Не заводить серверную часть.** Отсутствие сервера — не упрощение, а свойство:
картинка не уходит с машины, приложение работает офлайн и не зависит от того,
пропускают ли трафик. Ровно это и делает его доступным там, где недоступны
другие.

## Порядок

1. README по факту — **сделано**.
2. MCP-сервер: ядро + адаптер + три инструмента.
3. Вызов из `project-template`: новый проект получает иконки одной командой.
4. Мелкие пробелы — по мере надобности, не «на всякий случай».

**Огласки в списке нет намеренно.** Людям есть чем заменить, а тому
пользователю, которому заменить нечем, статья на Хабре не нужна — нужен
работающий инструмент в его руках.
